\begin{abstract}
We extended dida-trade with quorum validation, Multi-Paxos recovery and
pipelining, Fast Paxos, causal balance reads and dynamic membership.
The implementation separates decisions from ordered execution and transfers
accepted history before activating a new acceptor group. Controlled gRPC
checks and live scenarios exercise communication failures, concurrent
proposals, read races and interrupted transfers.
\end{abstract}

\section{Introduction}
Writes are ordered through a replicated Paxos log, while balance reads use
local state subject to the client's observed history. This report describes
the implementation choices for Steps~1--5, the defects found during review,
and the tests used to check the resulting behaviour.

\section{Step 1: Baseline Corrections and Debug Modes}
\label{sec:step1}

\subsection{Debug modes}
A gRPC interceptor applies debug modes to client and Paxos calls. The console
service is excluded so it can unfreeze a replica. \code{freeze} blocks incoming
calls on a monitor; \code{un-freeze} releases them without guaranteeing arrival
order. Slow mode adds a random delay of 500--4000\,ms per intercepted call.
\code{crash} schedules process termination after sending the console reply.
Replica state is held in memory and is lost on restart.

\subsection{Phase 1 and the baseline demonstration}
The original \code{PhaseOneBogusProcessor} ignores rejections, finishes after
the first reply and overwrites the reported value without comparing accepted
ballots. The replacement counts distinct promises, stops on rejection and
recovers the value with the highest accepted ballot for each classic slot.
Success requires positive quorum evidence: failed or pending calls are not votes.

The demonstration first decides request~101 in slot~0 on three replicas.
It crashes and restarts $S_1$ with an empty log, freezes $S_0,S_2$, and starts
ballot~1 at $S_1$ with request~102 pending. The bogus processor completes
preparation from its own empty reply. After the others unfreeze, $S_1$
executes~102 while $S_0,S_2$ retain~101. The fixed processor waits for a quorum
and recovers~101. This checks agreement, not crash recovery: the restarted
replica still lacks the original command body in this Schedule~A experiment.
The original processor remains selectable through
\code{-Ddidatrade.phase1=bogus}.

\subsection{Phase 2 also needs positive votes}
The phase-2 processor initially reported success unless it received an
explicit rejection. Communication failures could therefore finish collection
without a quorum but still allow the leader to decide the slot. Its result
is now derived from no recorded rejection and at least $q$ distinct positive
acceptances. Duplicate replies do not increase the count. A failed round
is retried, or abandoned if a higher ballot is reported. Learners also count
distinct acceptor ids, using the quorum required by the classic or Fast path.

\section{Step 2: Multi-Paxos}
\label{sec:step2}

\subsection{Multi-prepare and recovery}
Reusing phase~1 across slots requires recovering their history, not merely
checking that the ballot is unchanged. We extended the protocol reply with
a finite list of accepted entries: slot, value and accepted ballot.
For fixed membership, the leader requests the suffix from its first
unexecuted slot. The promise covers all slots; the reply lists only existing
acceptances. An omitted slot has no acceptance at that replica when the
snapshot is taken.

Recovery selects the highest accepted ballot per slot. Classic acceptances
identify the value to preserve; for Fast acceptances, recovery also considers
vote counts at that ballot and the scheduler's recovery threshold. Local
accepted state is kept separate from learned decisions, so an acceptor reports
its own votes. Preparation is reused until the ballot changes. Holes before
recovered entries receive pending requests, or no-ops when none are available.

\subsection{Pipelining and execution}
\code{MainLoop} can have phase~2 running for several slots simultaneously.
A window of 16 slots from the first unexecuted entry bounds outstanding work.
Decisions may finish out of order, but execution stops at the first undecided
slot or missing command body. Replies to clients follow execution, and the
window advances with the executed prefix.

Retries retain the same value for a slot within a ballot. Late callbacks from
abandoned ballots cannot decide the new attempt. Already processed request
ids are not executed again.

A single main-loop thread executes commands. RPC callbacks and relevant
incoming messages call \code{wakeup()}, while the loop uses \code{wait()}
without a polling timeout. Failed phase~1, phase~2 and \code{any} rounds
schedule a wakeup after 250\,ms, so retries do not depend on new traffic.
Notifications occur outside the server-state lock to avoid reversing the
loop's lock order. Automatic activation also makes the loop continue.

\section{Step 3: Fast Paxos}
\label{sec:step3}

\paragraph{Quorums.} Each schedule defines a classic quorum, a
super-majority and a recovery quorum: 3/4/2 in Schedule~B (5 acceptors)
and 2/3/2 in Schedule~A (3 acceptors). Phase~1 waits for a classic
quorum, so a value decided by a super-majority appears in at least
$\textit{quorum} - f'$ replies, with $f' = N - \textit{super-majority}$;
that is the recovery quorum. This holds because $f' < N/4$ in both
schedules.

\paragraph{Fast path.} After phase~1 of a fast ballot $b$, the leader
re-proposes the recovered slots with classic phase~2 and sends
\code{any(b, k)}, where $k$ is the slot after the highest recovered one.
It resends \code{any} until every acceptor confirms it: one acceptor
without \code{any} blocks every fast decision. Acceptors store
\code{any\_ballot} and \code{any\_from}, place each pending client
request in their next free slot $\geq k$, and send \code{learn(fast)}
directly to the learners.

\paragraph{Slot assignment.} Acceptors only agree if they place requests
in the same slots. Each acceptor keeps \code{fast\_placed}, a map from a
request to the slot where it voted for it in $b$. An entry is added on
every fast vote, so a request is not voted twice while its slot is open.
It is removed when that slot is decided with another request, so the
request can be placed again. The map is cleared when the ballot changes.
Two further rules keep acceptors aligned: requests already decided but
not yet executed are never voted again, and an acceptor starts voting
only after executing every slot below \code{any\_from}.

\paragraph{Learners.} For each slot a learner keeps, for the ballot it
is counting, a map from each value to the set of acceptors that voted
for it; votes from older ballots are ignored. Fast votes need a
super-majority, classic votes a classic quorum. When even the most voted
value cannot reach the super-majority with the acceptors that have not
voted yet, the slot has collided and the learner moves to $b+1$, whose
leader recovers it.

\paragraph{Recovery.} Phase~1 counts, per slot, the votes at the highest
ballot $j$. A value with at least the recovery quorum may have been
decided and is adopted; otherwise any value from $j$ is. A slot proposed
classically in $j$ has a single value, so no fast/classic flag is needed.

\section{Step 4: Causally Ordered Balance}
\label{sec:step4}

\subsection{Local reads with a causal lower bound}
Each replica maintains \code{executed\_index}, the length of its executed log
prefix. Write replies include their slot index plus one; balance replies
include the index associated with the returned state. The client retains
the maximum index observed and sends it as \code{minindex} with each read.
A replica waits until its executed index reaches that bound, then reads
locally without Paxos. The client contacts all replicas and uses the first
reply, so one sufficiently up-to-date replica is enough.

\subsection{Correct publication of results}
Two races required correction. First, a write's index must be stored before
its response is marked ready; otherwise the client can receive success with
an old index and later accept a stale read. Second, the balance and its index
must describe the same state. Command execution and advancement of the
executed index now hold the server-state lock; the read takes the same lock
to obtain both fields after waiting for its lower bound.

Reads use no log slot and can finish while the leader is frozen. They may
still be stale relative to other clients: this is causal ordering, not
linearizability. A replica that never catches up keeps its read RPC waiting,
since the wait has no timeout.

\section{Step 5: Dynamic Membership}
\label{sec:step5}

\subsection{Transfer before activation}
Schedule~C changes acceptors from $G_0=\{S_0,\ldots,S_4\}$ to
$G_1=\{S_2,\ldots,S_6\}$. A majority of the new group alone need not know
what the old group chose. We use preparation followed by activation,
inspired by Vertical Paxos~II. The console acts as master and retains the
last completed configuration.

For manual changes to ballots~2--4, \code{ballot} supplies the recovery
reference. Phase~1 reads its acceptors from slot~0, including slots already
executed by the leader: these must still reach the new acceptors. Recovery
uses each slot's accepted ballot to apply the classic or Fast rule.
The leader then transfers the history through pipelined classic phase~2,
even if the new ballot will later use Fast Paxos. Holes receive no-ops;
new client commands are held until activation.

Transferred values and learner notifications include command bodies, allowing
replicas that missed the client RPC to execute the history. Missing bodies
cause preparation to retry. Completion requires a positive new-group quorum
for every transferred slot; local execution or learning is insufficient.
An empty history completes after phase~1. The console can then send
\code{activate} with the explicit ballot. Stale or premature activation is
rejected. Until activation, the leader sends neither new client proposals nor
\code{any}. A late client RPC reuses its transferred request's stored result.

\subsection{Interrupted transfers}
A transfer can decide some slots before reporting completion. We reproduced
an error where ballot~2 decided request~201 at $S_5$, was interrupted, and
ballot~3 recovered only from $G_0$, deciding request~101 at $S_4,S_6$ for
the same slot. The console's old reference did not include the partial
transfer's decisions.

Recovery now reads both groups when the previous ballot's acceptors differ
from the reference group. It requires three promises from $G_0$ and three
from $G_1$, not a majority of their union. A shared acceptor counts once in
each group; duplicates do not add votes. Recovery retains the highest accepted
ballot per slot across the collected replies and applies its recovery rule.
Any classic transfer decision used three acceptors in $G_1$, so the new read
quorum of three in that group must intersect it.

In Schedule~C this additional quorum is needed for ballots~3 or~4 when the
reference remains~0 or~1. With a completed new-group reference, recovery no
longer requires removed acceptors $S_0,S_1$.

\subsection{Automatic recovery and limits}
A collision in Fast ballot~2 starts ballot~3 automatically. Fast votes imply
that ballot~2 was activated, and ballot~3 uses the same group. Its leader
therefore recovers from configuration~2 and activates after recovery quorums
complete. Initial membership changes and manually started preparations still
require explicit activation. An unavailable scheduled leader requires a
manual ballot change.

Replica state and the console's reference are not persistent. The protocol
covers the prescribed membership changes, not arbitrary restart recovery.
Transfer reads the whole prefix; its cost grows with the log because no
snapshots or truncation are implemented.

\section{Validation}
\label{sec:eval}
Validation combines controlled Java checks with real gRPC services and live
server/client scenarios. Build with \code{mvn clean install}; reproduction
commands and logs are documented under \code{validation/}.

\paragraph{Baseline and Multi-Paxos.}
The \code{bogus} and \code{fixed} modes of \code{validation/step1/run.py}
reproduce divergence and preservation respectively. The \code{processors},
\code{multiprepare} and \code{pipeline} scenarios in
\code{validation/part1/run.py} check quorum evidence, duplicate replies,
recovery across slots and overlapping phase~2. Peers hold an earlier slot's
replies while a later slot decides; execution must still wait. Further checks
cover old callbacks, the window bound, stable retry values, untimed waiting
and retries without new traffic. The debug test switches to classic ballot~1
before crashing a replica: two survivors suffice there, but not in
Schedule~A's Fast ballot~0.

\paragraph{Fast Paxos.}
\code{validation/step3/fast\_paxos.sh} runs twelve Schedule~B scenarios
on five replicas: the fast path; the super-majority boundary (with one
replica frozen the remaining four fast votes decide, with two frozen the
three votes neither decide nor count as a collision); collisions under
slow mode; fast/classic transitions; crash, freeze and rejoin; a frozen
leader; ballot changes under load; a dead next leader recovered from the
console; and a stress run. Each ends by checking that all live replicas
executed the same requests in the same order, none twice, and print the
same final state.

\paragraph{Causal balance.}
\code{validation/step4/run.py} checks reads without log entries, reads while
the leader is frozen, and a lagging replica waiting for the client's index.
\code{CausalChecks.java} pauses a write between its balance change and index
publication: a concurrent read must block and then return a matching pair.
It also checks that the write index is present when the response becomes ready.

\paragraph{Membership.}
\code{validation/step5/run.py} withholds old and new quorums, checks early
activation rejection, transfers missing bodies, reuses late-client responses
and continues after removing $S_0,S_1$. A regression test reconstructs the
interrupted-transfer divergence and checks that the actual leader preserves
request~201. Old-only and new-only recovery quorums are rejected. Another test
provokes a ballot~2 collision with removed replicas unavailable and recovery
writes initially failing: new requests wait for quorums and then resume
without console commands. These checks passed; they cover specific executions
rather than proving correctness for every message ordering.

\section{Conclusion}
The implementation supports concurrent consensus with ordered execution,
causal reads without Paxos and transfer of history across Schedule~C's
membership changes. The main corrections ensure that progress depends on
positive quorum evidence and that recovery includes decisions made during
unfinished transfers. Controlled tests exercise these failure cases and the
read-publication races. The remaining limits are in-memory state, full-prefix
transfer and indefinite waits for replicas that cannot catch up; durable
restart recovery is outside this implementation.
